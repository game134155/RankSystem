# Rank System 作业升级建议

本文用于给当前作业增加复杂度、完整性和可展示度。建议按「基础增强 -> 进阶功能 -> 高级亮点」分阶段实现，并在答辩时突出设计取舍。

## 一、基础增强（优先做，见效快）

### 1) 对局数据完整性校验

- 约束每场比赛的参与人数（例如固定 10 人）。
- 校验胜负数量平衡（例如 5 WIN / 5 LOSE）。
- 禁止同一玩家在同一场比赛重复出现（当前主键已覆盖，可在业务层补错误提示）。

价值：避免脏数据，体现你对「业务约束」和「数据正确性」的重视。

### 2) 自动更新玩家统计

- 录入比赛结果后，自动更新 `player_stats` 的 `mmr`、`wins`、`losses`。
- 根据新的 `mmr` 自动重算 `tier_id`（避免 MMR 与段位不一致）。
- 建议用事务包裹一次比赛的全部更新，确保原子性。

价值：体现完整业务闭环（录入 -> 结算 -> 排行）。

### 3) 排行榜与检索能力

- 增加按游戏维度的排行榜（按 MMR、胜率、胜场排序）。
- 支持玩家名称模糊搜索、分页、按段位筛选。
- 增加最近 N 场战绩查询（便于展示历史趋势）。

价值：更像一个可用系统，而不是只有表结构的演示项目。

## 二、进阶功能（提升“复杂度”）

### 1) 赛季系统（Season）

- 新增 `season` 表并关联 `match_history` / `player_stats`。
- 支持「切换赛季」与「赛季重置」。
- 保留历史赛季数据，支持跨赛季查询。

价值：引入时间维度，建模层次明显提升。

### 2) MMR 算法可配置化

- 将固定加减分改为可配置策略（例如不同段位、不同模式不同 K 值）。
- 预留规则配置表，后端按配置计算。
- 在文档中给出简化 Elo 公式说明。

价值：从“写死逻辑”升级到“规则驱动设计”。

### 3) 管理员审计与回滚

- 记录谁创建了比赛、何时修改、修改原因。
- 对管理员手工修正分数保留日志。
- 提供单场比赛回滚（撤销本场对玩家统计的影响）。

价值：体现可追溯性和运维意识，答辩很加分。

## 三、高级亮点（冲高分可选）

### 1) 异常行为检测

- 检测短时间异常连胜、固定对手反复交手等可疑行为。
- 给出告警列表供管理员复核。

价值：体现数据分析思维和系统安全意识。

### 2) 多维统计看板

- 最近 7 天胜率、段位变化轨迹、每个游戏的活跃度。
- 支持按玩家/游戏/时间区间过滤。

价值：从“管理后台”提升到“数据产品”。

### 3) 性能与可维护性优化

- 补充常用索引（例如比赛时间、玩家+游戏维度、排行榜排序字段）。
- 给复杂查询写 SQL 注释并说明执行路径。
- 增加基础压测与慢查询分析记录。

价值：体现工程能力，不只会“实现功能”。

## 四、数据库层可直接补充的改进点

- 对 `match_type` 做字典化（字典表或枚举约束），避免自由文本造成脏数据。
- 为高频查询增加组合索引（如 `match_history(game_id, start_time)`）。
- 保证 `player_stats.tier_id` 与 `mmr` 一致（触发器或统一在业务层更新）。
- 关键表补充 `created_at` / `updated_at` 字段，增强可审计性。

## 五、建议实现顺序（按作业时间分配）

1. **先做基础增强**：完整性校验 + 自动结算 + 排行榜（最容易产生可见成果）。
2. **再做一项进阶**：优先赛季系统或可配置 MMR（二选一即可明显拉开差距）。
3. **最后补文档和演示脚本**：准备 3~5 条关键 SQL / 页面截图 / 测试用例用于答辩。

## 六、答辩可直接使用的表述模板

- 设计目标：保证比赛数据可信、积分更新可追踪、排行榜可实时查询。
- 核心难点：多表事务一致性、段位与 MMR 同步、历史赛季可回溯。
- 工程取舍：强约束放数据库，频繁变化的业务规则放应用层，保证可维护性。

---

如果时间有限，至少完成「完整性校验 + 自动结算 + 排行榜」三件事，通常就能显著提升作业质量与复杂度观感。
