# 数据库实现说明

## 设计思路

数据按 **「谁、玩什么游戏、打得怎样」** 拆开存：账号在 **玩家表**，游戏目录在 **游戏表**，每个玩家在每个游戏一条 **统计表**（MMR、胜负、当前段位外键）。对局再拆成 **一场记录 + 每人一行结果**，既方便列表展示，又方便事后审计「赛前赛后 MMR」。

## 核心表各自解决什么问题

- **`player`**：登录身份（`player_id`、密码哈希、是否管理员）与展示用用户名；用户名唯一，供管理员按名字录入 5v5 名单时解析到 `player_id`。
- **`game` / `rank_tier`**：游戏列表与每个游戏下的 **段位阶梯**（段位名 + 最低 MMR 门槛）。段位不硬编码在代码里，改表即可调平衡。
- **`player_stats`**：复合主键 **（玩家，游戏）** 一行，表示该玩家在该游戏中的当前快照；对局结束后只更新对应行。
- **`match_history`**：表示「发生了一场比赛」：哪个游戏、谁创建、何时开始等。
- **`match_player_result`**：该场比赛中每个参与者一条：胜负、MMR 变化、赛前赛后值；与 `match_history` 外键关联，主键约束 **同一场同一玩家只有一行**。

外键把表串成一张 **有向依赖图**，避免孤儿记录（例如没有玩家的对局明细）。

## 脚本分工

- **`schema.sql`**：建库、建表、约束与字符集（常用 utf8mb4）。这是结构的「契约」，应用逻辑默认表名与字段与此一致。
- **`seed.sql`**：演示账号、示例游戏与段位、以及初始统计。密码在种子数据里用与后端一致的 **哈希方式** 写入，便于本地一键跑通登录。

## 与应用的配合方式

后端不写动态 DDL，只 **读写固定结构**：读时用 JOIN 拼页面；写时尤其在录入比赛时 **多表连续更新**，依赖事务保证要么全成功要么全撤销。数据库负责 **持久化与约束**，业务规则（例如怎么算加减分）在应用层实现，便于迭代公式而不改表结构。
